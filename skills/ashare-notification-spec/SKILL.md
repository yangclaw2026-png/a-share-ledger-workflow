# 通知与定时任务规范（横向）

主技能 `a-share-investment-workflow` 的横向子技能，适用于所有步骤的自动提醒与定时任务。

## When to Use

- 新建、修改、恢复或取消任何投资相关定时任务。
- 需要决定是否提醒、发到哪里、发什么内容。
- 排查通知未送达。

## 🔴 执行纪律（本工作流强制·优先级最高）

**本节优先级高于本技能全部内容，冲突以本节为准。**

### 一、本技能不可跳过的项

| # | 项 | 不做会怎样 |
|:-:|---|---|
| 1 | 新建/修改/恢复/取消任何定时任务前，先 `skill_view` 本技能 | 渠道、静默、格式三处规则都会漏 |
| 1b | 🔴 **发邮件的任务必须挂 `hermes-stock-mail` 技能**，不得只靠 prompt 手抄邮件规则 | 规则散落在 prompt，抄漏/抄旧/抄互相矛盾（已发生）|
| 2 | 🔴 **deliver 显式写 `feishu:<你的chat_id>`，不带 `platform:` 前缀** | 带前缀 → `delivery_failed`（实测） |
| 3 | 🔴 **通知数值一律明文**（成本/现价/ATR/阈值/超出幅度），不得用口径行代替 | 用户看到等于没看到（实测事故：无数值邮件） |
| 4 | 🔴 **无实质变化 → 飞书与邮件都不发**。no_agent 的 `_send_mail` 必须有 `and rendered` | 静默分支发出空邮件 |
| 5 | 🔴 **不用 `origin`/WebUI 投递** | WebUI 不在白名单，拖挂整条投递（连飞书也失败） |
| 6 | 技能改名/合并/删除后 → 逐个 `hermes cron edit <id> --remove-skill <旧> --add-skill <新>` 再 `cron list` 复查 | 任务静默失效，`cron doctor` 查不出来 |
| 7 | 🔴 **cron 引用写完整任务名，永不写 ID**；简称会匹配失败 | 引用失效 |
| 8 | 收尾/排查通知时**查 `cron/executions.db` 的 `source`/`delivery_outcome`**，不以手工 `run` 结果为准 | 手工 run 是 `source=direct`，必然报 not configured，判断全错 |
| 9 | 🔴 **非持仓任务的结论必须同时追加到云文档 `04_自动通知`**（`feishu_append_notice.py --task "<任务全名>" --file <正文.md>`）；**持仓类（第7步）不写云文档** | 三通道只落地了两个（2026-10-09 前的真实状态：无 prompt、无脚本在写）|

### 二、本技能专属红线

- 🔴 **提醒不是交易指令**。自动任务不得改持仓、不得生成未确认价格线、不得买卖、不得自行创建新任务。
- 🔴 **通知正文（飞书/邮件）可明文数值；隐私边界只到飞书云文档** —— 台账同步硬排除 `持仓中/`，云文档 `04_自动通知` 硬排除持仓类任务（脚本闸门）。两者不冲突。
- 🔴 卫星 profile **绝不可加平台凭据**（`duplicate_credential` 致命）；`platforms.feishu.enabled` 保持 `false`。
- 🔴 `oc_` 开头是 chat_id，`ou_` 开头是 open_id —— 填错投递失败。
- 🔴 **cron 频率/ID 以 `hermes cron list` 的 `next_run_at` 为准**，本技能第3节快照易过时，不作准。
  🔴🔴 **但 `hermes cron list` 的 `Schedule:` 行本身不可信**（2026-10-07 实测）：长线观察位真实 expr=`5 20 * * 5`（周五 20:05），CLI 却显示 `0 9 * * 1`（周一 09:00），而同一区块的 `Next run: 2026-10-09T20:05` 又是对的 —— **同一区块自相矛盾**。
  ✅ **核对频率的唯一可靠办法**：直接读 `cron/jobs.json` 的 `schedule.expr`，再与 `next_run_at` 交叉验证两者是否自洽（时刻与星期几都对得上）。
  🔴 **根因已定位（2026-10-07）**：jobs.json 里有个陈旧字段 `schedule_display`，CLI 显示读的是它。当它是自然语言（`every monday 8:30am`）时正常；当它是**脏 cron 串**时会把真值盖掉 —— 长线观察位 expr=`5 20 * * 5` 而 display=`0 9 * * 1`。修法：`hermes cron edit <id> --schedule "<真值>"`，CLI 会重写该字段（实测已修好，next_run 不变）。
  ⛔ **不得只看 `hermes cron list` 就改文档里的时间** —— 我因此把文档改错过一次（周五 20:05 → 周一 09:00），靠 jobs.json 才抓回来。
- 全局三条硬规则见 `a-share-investment-workflow`《执行纪律》一节。

### 三、收尾自查

- [ ] deliver 是 `feishu:oc_...`（无 `platform:` 前缀、无 origin）
- [ ] 🔴 **发邮件的任务已挂 `hermes-stock-mail` 技能**（新任务必查）
- [ ] 🔴 **飞书与邮件内容同源**（都用完整 markdown，非一个完整一个简略）
- [ ] 邮件用 `--body-file`，未用 `--body` 传长文本
- [ ] 通知正文数值明文，无口径行代替
- [ ] 静默分支未发空邮件（`and rendered` 在位）
- [ ] 🔴 非持仓任务的结论已追加到云文档 `04_自动通知`（`feishu_append_notice.py`）
- [ ] 🔴 持仓类任务**未**写云文档（脚本会拒绝，不得绕过）
- [ ] 涉及持仓提醒 → 已确认不上传云文档
- [ ] 未把提醒写成交易指令、未自动推进下一步

## 1. 渠道（本工作流固定要求·2026-10-09 更新为三通道）

⭐ **所有自动化通知走「飞书 IM ＋ 邮件 ＋ 飞书云文档 04_自动通知」三通道**（本工作流明确）。
🔴 **唯一例外：第7步／持仓类通知不上云文档**，只走飞书 + 邮件（覆盖旧的「只写元信息」做法）。

| 通道 | 目标 | 实现 |
|---|---|---|
| 飞书 | `feishu:<你的chat_id>`（deliver，chat_id 是 `oc_` 开头的那串）| 🔴 **不带 `platform:` 前缀**——加了会 delivery_failed（详见 `hermes-cron-operations` 第九·六节关卡 5）|
| 邮件 | `<你的邮箱>`| `mailer.py --subject ... --body-file ...`；no_agent 任务在脚本内调。🔴 **一律完整版，含持仓数值** |
| ③ 云文档 | 云文件夹 `04_自动通知`（token 从环境变量 `FEISHU_FOLDER_NOTICE` 读）| `python3 scripts/feishu_append_notice.py --task "<cron 任务全名>" --file <正文.md>`（一任务一文档·追加）。🔴 **任务名含「持仓」会被脚本直接拒绝** |
| ⚪ 例外 | 云文档同步 | `sync_ledgers_to_feishu.py`（只写飞书云文档，不发邮件——它不产生"提醒"）|

### 🔴 通知内容一律明文（本工作流强调）

- **数值直接写进消息与邮件**：成本、现价、ATR、阈值、超出幅度、涨跌幅、估值分位——全部显式列出。
- **隐私边界只针对飞书云文档**（台账同步硬排除 `持仓中/`），**不针对通知消息本身**。
- 正确：`现价 45.12｜加权成本 40.0｜20日ATR 1.53｜阈值 43.06｜超出 2.06`（模板见 `profit_guard.py::_render_for_delivery`）
- 📌 **邮件一律完整版**：与飞书消息内容一致，含全部结论、数字、表格，**不做精简**。用 `mailer.py --body-file`，markdown 表格会自动转成 HTML 真网格。用户不再需要为「飞书上看格式太累」去查本地终端。

### 🔴 三通道同源原则（本工作流裁定·唯一权威）

**飞书、邮件、云文档三者必须同源：内容一致，不得一个完整一个简略。**

| 场景 | 飞书消息 | 邮件 | 云文档 `04_自动通知` |
|---|:-:|:-:|:-:|
| 候选／方向／第5步任务 | ✅ 完整 | ✅ 完整 | ✅ 每任务一份文档，追加该次正文 |
| 🔴 持仓类（第7步）任务 | ✅ 完整 | ✅ 完整（含持仓数值）| ⛔ **完全不上云文档**（2026-10-09 裁定，覆盖旧「只写元信息」）|
| 静默（无实质变化）| ⛔ 不发 | ⛔ 不发 | ⛔ 不追加 |

**落地要求**（每个发邮件的任务都适用）：
1. 🔴 **先写完整 markdown** 到 `/tmp/<任务id>_<日期>.md`，再用 `--body-file` 发。
2. 🔴 **不得只发一句摘要**。曾发生：持仓类邮件被 2026-10-05 的旧规则压成
   「该执行持仓复核了。详细内容请在飞书查看」——用户反馈「飞书上看格式太累」。
3. 🔴 **不得用 `--body` 传长文本**（shell 引号嵌套易失败）→ 统一 `--body-file`。
4. ✅ **表格用标准 markdown 管道表**，`mailer.py` 自动转 HTML 真表格（网格线＋表头底色）。
5. ✅ **结论先行**；数字带单位与口径；事实/推断/待核实分开写。
6. ✅ 末尾保留「仅供参考，不构成投资建议」。
7. 🔴 **静默规则两通道一致**：判定 SILENT → 飞书与邮件**均不发**，不得一个发一个不发。
8. 🔴 **发信失败不阻塞飞书**，在飞书末尾附「邮件发送失败：<原因>」。

**🔴 新增/修改 cron 时的检查项**：
- ⛔ **不得只靠 prompt 手抄邮件规则** —— 必须 `--add-skill hermes-stock-mail`，
  邮件规则以技能为唯一权威。2026-10-07 体检发现：该技能存在却**一个 cron 都没挂**，
  导致 prompt 里的手抄片段互相矛盾（这正是旧规则残留至今的原因）。
- ✅ 改完用 `hermes cron list` 或读 `jobs.json` 复查 `skills` 字段真的加上了。

- **无实质变化 → 飞书与邮件均不发**。飞书安静 = 没有变化，不是没运行（`delivery_outcome=suppressed` 是正常预期）。
- 🔴 **no_agent 脚本的 `_send_mail` 必须在 `rendered` 非空时才调用**。否则静默分支会发出一封**只剩追加口径行的空邮件**（实测事故：`profit_guard.py` 曾因此发出无数值邮件）。正确写法：
  ```python
  rendered = _render_for_delivery(result).strip()
  if rendered:
      print(rendered)
  if result.get("_mail") and rendered:      # 🔴 `and rendered` 不可省
      _send_mail(result, rendered)
  ```
- 不使用 `origin`/WebUI 来源投递：WebUI 不在 Hermes 投递白名单，加了 `origin` 会拖挂整条投递（连飞书也失败）。
- `ou_` 开头是 open_id，不是 chat_id；chat_id 是 `oc_` 开头（两串都从飞书后台取，勿混用）。

## 2. 多 profile 架构与坑（实测）

如你的 Hermes 是多 profile 网关（`gateway.multiplex_profiles: true`），工作流 profile 通常是**无凭据的卫星 profile**。

1. **手动 `cronjob(action='run')` 不能用来验证平台投递**——它走 `source='direct'` 的后台委派进程，拿不到主网关的实时适配器，必然报 `platform 'feishu' not configured/enabled`。真实定时触发走 `source='builtin'`（网关进程），投递正常。验证方法：把任务排到 `in 2m` 让它自然触发，或查 `cron/executions.db` 的 `source`/`delivery_outcome` 两列。
2. **绝不要给卫星 profile 加平台凭据**：`duplicate_credential` 是致命错误；把 `platforms.feishu.enabled` 改成 true 会让网关报 `[MULTIPLEX] Profile 'x': skipping platform 'feishu' - adapter creation returned None`。保持 `enabled: false`，让主网关适配器按 route 投递——共享适配器由 **root config 的 `gateway.profile_routes`** 定义，不在本 profile 里。
   - 两个 id 不可混用：`oc_…` 是 **chat_id**（投递目标）；`ou_…` 是 **open_id**，不是 chat_id，填进去会投递失败。
3. 改 profile config 用 `hermes config set`；`patch`/`write_file` 工具会拒绝写 Hermes config。
4. 改任务后要读运行记录/`cron/executions.db` 验证，而不是只看配置。
5. **技能重构后必须同步更新 cron 任务的 `skills` 附件。** 已删除的技能名（如 `investment-ledger`）留在任务里不会让任务报错，`cron doctor` 也查不出来，但任务运行时拿不到该阶段的流程规范——属于静默失效。技能改名/合并/删除后，逐个 `hermes cron edit <id> --remove-skill <旧> --add-skill <新>`，再用 `cron list` 复查。
6. **真实自然触发已验证可用**（2026-10-04 23:43，一次性探针 `source=builtin`、`delivery_outcome=delivered`）。验证方法：建一个 `--repeat 1` 的 `2m` 探针任务、`deliver` 指向飞书私聊，等它自然触发，查 `executions.db` 的 `source`/`delivery_outcome` 两列，然后删掉探针。

## 🔴 消息格式规范（本工作流确认：默认用交互卡片）

| 场景 | 格式 |
|---|---|
| **总结 / 报告 / 含表格 / 多层结构** | ✅ **`interactive` 交互卡片**（`column_set` 真网格 + `hr` 分隔）|
| 极短提醒（1 行、无表格） | `text` 即可 |
| 持仓数值提醒（11:20 / 14:40）| **`text` 明文数值** —— 走 `no_agent`（0 token），卡片 JSON 更长且无格式收益 |

📌 **判据**：内容有表格或多层结构 → 一律卡片；纯一行数值 → text。
**为什么持仓提醒例外**：那两个任务是 `no_agent` 脚本，数值本身已明文，不靠排版传达。
规则与三个坑见 `feishu-im-message` 技能。

唯一硬约束是命名规范（见下）：台账里引用的任务名必须与你实际建的 `name` 逐字一致。

🔴 **cron 引用一律写完整任务名，永不写 cron ID** —— ID 会随重建变化（改任务名后 ID 引用必然失效，已踩坑两次）。
📌 **必须逐字照抄 `jobs.json` 里的 `name`**，包括 `｜` 分隔与括号内容；**校验器按 `name` 精确匹配，简称（如「门槛复查」「台账同步」）会匹配失败**。
（详见 `ashare-ledger-standard` 与 `a-share-investment-workflow` 飞书同步边界）

⭐ **降噪经验**：任务曾从 20 个精简到 9 个 —— 方向级监控改为写进 `流程状态表.md`、由用户手动触发，不必每个方向都建 cron。

⚠️ **以 `hermes cron list` 的 `next_run_at` 为准**，不以本表为准（本表示例，不跟随你的实际任务更新）。

## 4. 提醒优先级（默认顺序）

1. 用户明确设定的价格阈值或退出规则触发（以用户规定的价格、时点、确认方式为准）。
2. 原投资理由被可信证据实质削弱或失效；不要把股价下跌本身直接等同逻辑失效。
3. 相关全球产业、海外对标、供需/价格/订单/资本开支或产业链轮动出现持续且可能改变判断的变化。相关性不是资金因果，单日涨跌不足以确认轮动。
4. 公司重大公告、业绩、订单、客户/供应链、治理或融资变化。
5. 价格、成交和技术状态作为辅助预警，不单独自动导出买卖结论。

## 5. 提醒质量要求

- 每条非机械价格提醒至少说明：发生了什么、数据日期与来源、为何与该股票/假设相关、哪些是已证实事实、哪些是推断、置信限制及是否需要复核。
- 未能核实的数据不得写成事实。
- **只提醒可能改变用户行动、持仓风险或投资假设的重要变化**；普通行情/新闻尽量静默。
- 提醒**不是交易指令**；用户本人决定并执行所有买卖。

## 6. 按阶段降噪

- 方向/候选阶段：周期性扫描或用户指定条件触发，不创建持仓风险任务。
- 等待买入条件：围绕用户确认的观察条件；未触发时静默。
- 已持仓：优先推送用户设定退出规则和会改变投资理由的重要变化；其余静默或按约定汇总。
- 已卖出：用户告知后更新状态，按用户结果取消/调整持仓任务，保留历史记录。
- 多个标的（目标规模约20只）按阶段和优先级管理；不要机械地为每只股票每天生成长报告。

## ⭐ 三通道留档：云文档 `04_自动通知`（2026-10-09 起真正落地）

用户要求：cron 通知发**飞书 + 邮件 + 飞书云文档「04_自动通知」**；**第7步（持仓类）不发云文档**。

**执行方式**（一行命令，脚本自带隐私闸门与正文抽取）：

```bash
python3 scripts/feishu_append_notice.py \
    --task "候选监控｜候选门槛复查" \
    --file $HERMES_HOME/cron/output/<任务id>/<时间>.md
```

- **一任务一文档，追加不覆盖**（本工作流要求）；文档名 = 任务名去掉 `持仓监控｜/候选监控｜/方向监控｜/第N步｜` 前缀
- 🔴 **持仓类任务传进去会被脚本直接拒绝**（任务名含「持仓」即拒）—— 第7步只走飞书 + 邮件
- 🔴 **静默时不调用** —— 无实质变化不追加
- 🔴🔴 **cron 输出文件是完整对话记录（含 Prompt 与技能全文）**，脚本自动只取最后一次 `## Response` 之后的正文；无该标记且文件 >4000 字符 → 拒绝写入。
  **实测事故**：曾有人直接用 cron 输出整份追加，把几十 KB 提示词灌进云文档。**绝不整份上传 cron 输出。**
- 索引 `.feishu_docs.json` 的 `"notices"`：`{任务全名: doc_token}`；**新建后立刻落盘**（防超时被杀后重跑产生重名文档）
- 📌 留档由本技能驱动：启用的 agent 任务均挂本技能 → 每次运行按上表规则执行（持仓类不留档）。
- 🔴 **本工作流明确决定：不往 cron prompt 里加显式指令，先只靠本技能驱动，跑一两轮看效果再定。** 不得自作主张去 `cron edit` 改 prompt——要改先问。
- 相关脚本与端点见 `feishu-doc-sync` 技能。

## 7. 自动任务的权限边界

- 自动任务只做**有范围限制的证据扫描**或**盈利保护启动条件检查**；不能更改持仓数量、生成未确认的价格线、买卖，或自行创建新任务。
- 启用/修改自动监控必须获得用户明确授权；不确定的阈值留给用户决定。
- 测试交易日/节假日逻辑用 monkeypatch `date.today()`，不要改系统时间；同时 patch 行情函数制造模拟价格。
- 告警分档要检查每档是否可达：阈值必须严格递增，否则某档永远不可能命中。
