# 第6步：买入前讨论与独立核验

主技能 `a-share-investment-workflow` 第6步子技能。门禁按“**每一笔拟评估的买入/加仓**”计算。**顺序不可颠倒：用户与 Hermes 先讨论 → Pi 与 OpenCode 独立核验 → 用户最终决定。**

## When to Use

- 用户希望评估一笔具体买入/加仓（首次建仓或后续批次）。
- 出现实质影响原投资理由的重大变化，需单独核验（属风险复核，不触发买入门禁）。

## 🔴 执行纪律（本工作流强制·优先级最高）

**本节优先于本技能其余内容。冲突以本节为准。**

### 🔴 第一条：本步不得自动启动

**门禁只有用户主动发起才能启动。** 用户没明确要求评估这笔交易，就停在第5步。

- 不许因为「条件达到了」就自己开工
- 不许因为「快触发了」就预先准备
- 不许把分析结论当成门禁已通过

### 本步不可跳过的项

| # | 强制项 | 不做会怎样 |
|---|---|---|
| 1 | **顺序不得变**：用户与助手先讨论 → Pi/OpenCode 独立核验 → 用户决定 | 跳过独立核验 = 单一模型的判断冒充「双 AI 验证」 |
| 2 | 任务卡必须完整（含标准结构全部字段）| 缺字段的核验请求会被 Pi/OpenCode 随意补全 |
| 3 | 独立性：两个 AI 独立跑，不得把一方的结论喂给另一方 | 串通 = 假交叉验证 |
| 4 | 最终由**用户决定**，助手只提供信息 | 越过用户 = 违反「永不下单」边界 |

### 本步专属红线

**不得自动下单、不得建议调仓、不得自创卖出价。** 门禁产出是「建议+证据」，不是指令。

> 全局三条硬规则（不凭记忆执行／跳过须显式写明／缺数据就停下来报）见主技能
> `a-share-investment-workflow` 《执行纪律》一节。

### 收尾自查

- [ ] 用户已主动发起本步（不是我自行启动）
- [ ] 三阶段顺序严格按序，每阶段产出都落地了
- [ ] Pi 与 OpenCode 独立核验都跑了，且互相独立
- [ ] 最终结论是「待用户决定」，没有代替用户拍板

## 门禁触发

- 标的须已过“是否值得跟踪”筛选并处于跟踪阶段。
- 即使条件到位，也只有用户希望评估时才启动；不能因价格波动或信号接近自动发起。
- **重大风险复核与买入门禁分开**：风险复核不代表买入建议，也不意味着用户要交易。

## 三分支

- **首次建仓**：走完整讨论与独立核验流程。
- **后续分批买入/加仓**：聚焦复核（该批预设确认条件是否满足、原逻辑是否仍成立、估值与组合风险是否变化），Pi 与 OpenCode 仍须独立核验本次关键证据与反证。
- **重大风险复核**：只针对受影响假设核验，不包装成买入讨论。

## 流程（严格按序）

1. 用户提出想买的股票与初步理由；先核实准确代码/公司主营，询问关键理由、预期持有周期和最关心的不确定性。
2. Hermes 与用户讨论全球市场环境、全球产业方向、产业链环节、轮动和个股位置，形成初步回应。**允许保留分歧，不要求先达成共识。**
3. 把用户原始理由、双方观点、已核实事实和未决问题整理成**相同任务卡**，交 Pi 与 OpenCode **独立**分析；不把一方结论透露给另一方作先验。
4. 汇总对照表：①核实事实状态（双方独立核实/单方核实/来源冲突/无法核实）及来源日期；②双方核心判断及依据；③关键分歧、代表性原话及是否可能改变判断；④条件式结论、未决事项、待补证据。
5. 给用户三状态：**买入 / 不买 / 继续跟踪**（均由用户决定）。
6. 用户决定买入 → 等待其实际操作并主动告知后再建底账（第7步）；继续跟踪 → 回第5步；不买 → 记录决定，不配持仓监控。

## 任务卡标准结构（试行）

共同字段：①任务信息（标的名称/代码、日期、任务类型：首次买入/后续加仓/重大风险复核）；②本次待回答问题与范围；③用户原始投资逻辑、产业环节与传导路径，区分观点与已核实事实；④前次结论、关键假设与本次变化；⑤关键经营/产业/估值/行情/组合证据（来源、日期、单位、比较窗口、口径；缺项明确列出、不猜）；⑥需检验的风险与反证；⑦要求双方分别核实事实，列支持证据、反证、待核实项与分歧，不把任务卡内观点当既定事实。

附加模块：首次买入→完整初始评估问题；后续加仓→本批预设确认条件及满足情况、相较前次变化、估值与组合风险；重大风险复核→触发事件、受影响假设、可能改变的判断。

## 独立性与汇总原则

- **多 Agent 意见一致 ≠ 独立验证**：独立性来自不同证据和不同检验任务，不是模型名字不同。
- 一致不自动等于事实已证实；不以多数投票代替证据；不强选胜方、不合成虚假总分。
- 关键事实冲突或分歧足以改变判断 → 针对争点复核；仍无法解决则明确标未决。
- 轻量门禁仅摘录关键原话，不必输出完整辩论记录。
- 结论**不构成交易指令**；助手永不下单。

## ⭐ 批次等待盯盘（本工作流确认·通过门禁后立即启用）

第6步通过门禁后，必须先与用户讨论并记录第1、2、3批全部买入条件、判定口径、计划数量/比例、确认日期与版本。第6步监控只覆盖第1批；不监控、不提醒第2、3批。首笔实际成交后进入第7步，第7步先原样继承第2、3批条件，再基于成交后的新证据与用户讨论是否调整；不得静默覆盖旧条件。

### 🔴 必须分清职责

| | 第6步门禁 | 第6步买入监控 | 第7步 |
|---|---|---|---|
| 负责内容 | 用户主动启动的买入讨论与核验 | 仅第1批已确认条件 | 已持仓保护＋第2、3批未执行条件 |
| 批次规则 | 先讨论并确认全部三批条件 | 只读取第1批条件 | 继承第2、3批条件，再与用户讨论是否调整 |
| 启停边界 | 用户主动启动 | 首笔实际成交后停用 | 首笔实际成交后启用 |
| 决策权 | 用户 | 用户 | 用户 |

第6步信号触发只提示，不代表用户同意买入；不自动下单。用户报告买入或卖出后，第7步核实交易日与成交事实，更新原台账并刷新 cron。

### 触发条件与机器可读标记

门禁时与用户逐股确认三批的触发条件、精确定义、判定时点、数据口径、计划比例和复核节点，并写入台账 §3.1。第7步只按台账已确认内容工作；需要调整时先说明新证据及新旧条件差异，取得用户确认后新增版本并保留旧版。

第7步当前支持两种可选规则标记：
- `batch=2 monitor_rule=B2_MACD_VOL_1_5`：MACD 金叉事件且量比≥1.5。
- `batch=3 monitor_rule=B3_CLOSE_MA60_FLAT_ANTICHASE`：14:40 实时价≥以日K收盘序列计算的 MA60、MA60 不下行，再依相对第1/2批成交均价做防追高分档。

仅当用户确认条件完全一致时才写相应标记。其它自定义条件不加近似标记；第7步报告 NEED_CONFIRM，待核验后处理。14:40 尾盘快照提醒不等同正式收盘确认。

### cron 设计

- 第6步：通过门禁并确认三批条件后，单股一个任务，只监控第1批；首笔实际成交后停用。
- 第7步：原有持仓监控任务在14:40兼管后续第2、3批；11:20只做持仓保护。每次用户报告买入/卖出后，按台账更新批次与持仓，并核对/刷新 cron。
- 每批提醒只通知一次；条件解除后重新满足才重新提醒。

### 三档 action（沿用 Python 前置范式）

| action | 条件 | 行为 |
|---|---|---|
| `REVIEW` | 第1批条件满足或数据/台账需确认 | 提醒用户，第6步仅监控第1批；后续批次由第7步接管 |
| `SILENT` | 第1批条件未满足，且无数据/风险变化 | 静默（最常见分支）|
| `FAULT_ONCE` | 台账缺失或行情取数失败 | 告知一次，不刷屏 |

🔴 **台账缺失必须报出**（标「台账缺失待补」），不得静默跳过 —— 那是第6步台账制度执行情况的自我暴露。

## 输出与停止条件

讨论记录 + 任务卡 + 独立核验对照 + 三状态结论交给用户即停，等待用户决定。

## 🔴 阶段变更 = 更新流程状态表（三层保障）

标的进出本步（新增／移出／降级／清仓）时**当次**更新 `股票台账/流程状态表.md` 对应行，只写「名称 (代码)」；细节进单股台账。🔴 **同一代码不得出现在多个阶段行。**

三层保障：① 本要求；② `validate_ledgers.py` 台账↔状态表双向一致性（跨行重复／有台账未登记／标第5-7步但无台账）＋台账正文↔`bench.json` 门槛数据一致性；③ 周一 08:12 `台账同步`（no_agent）自动跑校验，不一致→飞书告警。

🔴 目录与 cron 是自动扫描的（建台账即纳入），**只有流程状态表是手工的** —— 唯一会漏的环节。
