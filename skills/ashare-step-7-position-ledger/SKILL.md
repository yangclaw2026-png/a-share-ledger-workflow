# 第7步：建仓承接与持仓管理

主技能 `a-share-investment-workflow` 第7步子技能。**用户报告实际成交后**才启动本步；候选股不算持仓。助手永不执行交易。

## When to Use

- 用户告知实际买入/加仓/减仓/卖出。
- 用户问“该拿多少仓位”“要不要分散”“止损设多少”。
- 需要更新持仓台账、组合风险或盈利保护线。
- 常规持仓跟踪与提醒。

## 🔴 执行纪律（本工作流强制·优先级最高）

🔴 **本节优先于本技能其余内容，冲突以本节为准。**

### 本步不可跳过的项

| # | 强制项 | 不做会怎样 |
|---|---|---|
| 1 | **台账是成本的唯一权威源。** 只认《交易记录》表里方向为买入/加仓、且数量等于持仓量的那一行 | 从正文说明文字抓数字会把股价当成本，阈值直接算错 |
| 2 | **台账读不到 / 解析失败 = 报故障，绝不用内置基线凑数** | 用旧成本算出的阈值是错的，会漏报或误报触发 |
| 3 | 成本口径含手续费（用户提供的成交价） | 不含手续费的阈值偏低 |
| 4 | 🔴 **持仓数据永不上云** —— `持仓中/` 目录级硬排除 | 违反用户明确的隐私边界 |
| 5 | 🔴 **三模块的**手填**参数（两档回撤、两档亏损线、仓位上限）以台账为准，脚本只读不算；峰值属市场客观数据，由脚本自算（见 9.0.1）** | 风控边界由脚本拍板 = 越权；峰值手填会随每次新高过期 |
| 6 | 🔴 **模块三给加仓建议前必查单股仓位上限**；缺上限时直接报「无法给建议·缺仓位上限」 | 无上限则算不出还能买多少，加仓建议是空谈 |
| 7 | 🔴 **上涨加仓必须有回踩确认**，不得只按涨幅触发 | 实测同规则在周期股与成长股结果相反（周期股 −5.1% vs 成长股 +34.0%）|
| 8 | 🔴 **同一档位只提醒一次**，状态变化或用户处理后才可再报 | 每天推无意义报告是打扰 |
| 9 | 🔴 **用户买卖后必须先确认当日是否交易日**（`scripts/trading_day.py`），再写台账 | 节假日误判会让峰值起点和成本整条线算错 |
| 10 | 🔴 **禁止硬编码节假日表**；禁止用「周一至周五=交易日」粗判 | 调休的周六是交易日，春节所在的周五是休市 |

### 本步专属红线

**价格类现象（跌、破均线、回撤扩大）一律不是失效条件**，只触发复核；失效只由公司端证据判定。

> 全局三条硬规则（不凭记忆执行／跳过须显式写明／缺数据就停下来报）见主技能
> `a-share-investment-workflow` 《执行纪律》一节。

### 收尾自查

- [ ] 成本与**峰值**均从台账读到，不是内置基线
- [ ] 三模块判定用的参数全部来自台账（未由脚本自行拍板）
- [ ] 🔴 若给加仓建议：已确认仓位上限、逻辑未失效、过了组合层检查
- [ ] 🔴 触发亏损保护时：已同时报告公司端证据（纯价格 vs 真有硬信号）
- [ ] 🔴 未把上涨加仓按涨幅直接触发（必须含回踩确认）
- [ ] 🔴 未对同一档位重复提醒
- [ ] 台账已更新，且**未**同步到飞书云文档
- [ ] 三模块监控已配（11:20 ＋ 14:40 两观察点）
- [ ] 没有代替用户做买卖决定

## 核心原则

1. **先有底账，再有报告。** 关系链：`股票代码 → 投资假设 → 证据及时间 → 决策版本 → 实际操作 → 后续检查结果`。每只股票一个 markdown 即可，数据库不是必需。
2. **数字从代码来，不从模型记忆来。** 但“数字来自代码”≠数字正确，必须保留来源URL、获取日期、计算口径（复权方式、窗口长度）。
3. **事后回忆不得冒充事前记录。** 补建旧持仓标“事后回忆”；判断修正保留旧版本，追加不覆盖。
4. **允许结论是“不交易”或“维持不动”。** 禁止为了输出而制造确定性。
5. **止损价不是亏损上限**（见第6节）。
6. **多 Agent 意见一致 ≠ 独立验证**（见 `ashare-step-6-prebuy-gate`）。

## 1. 确认日期与数据

先 `date` 确认今天。周末/节假日说明“行情截至最近交易日”，不用陈旧数据冒充实时。数据源、解析方法与已知坑见主技能 `a-share-investment-workflow` 下挂的《数据源、引用规范与历史对比铁律》参考文件。

## 2. 交易记录（每笔追加，不覆盖）

对每只实际买入的股票维护一份连续跟踪文档；每笔交易追加：日期、买卖方向、价格、数量、费用（若提供）、交易后剩余持仓、用户计划的卖出额度/价格及当时理由。**保留批次和历史，不覆盖；估算价与实际成交价严格区分。**

并列维护：①剩余持仓数量、分批/加权成本与未实现盈亏；②本轮交易周期累计已实现+未实现盈亏。费用/税费缺失时注明，不猜；说清成本分摊方法，避免把部分卖出所得误当成剩余仓位降本。

**成本口径：** 本账户用户口径为——**成交价一律含手续费，费用不单列、不另行加计**（本工作流确认）。因此无需逐笔询问费用；台账、提醒和比价一律直接用该含费成交均价。仅当用户**明确给出未计费价格**（如“是净价/我要另付佣金”）时，才需在台账专项标注口径差异并另行说明；未声明的成交价一律视为含费。同一账户内各标的、各时点的比价必须使用同一口径。成交价是否为 VWAP 仍需单独确认——用户说“含手续费”不等于已声明是 VWAP。

## 3. 分批建仓框架（30/40/30，试行）

单股目标仓位分三批买入 30%＋40%＋30%，目的是分散一次性建仓的时点风险，同时避免因只等下跌而错过上涨。

- 上涨时：不因涨而自动追买，也不机械等回调；若原逻辑成立、有相关确认证据且估值与组合风险可接受，可评估下一批。
- 下跌时：先判断是市场/短期扰动还是产业/公司逻辑受损；逻辑未失效、估值与风险回报改善且无关键反证，方可评估，不能仅因跌价加仓。
- 两条路径都复核逻辑、估值、风险和组合仓位；不合适可暂缓或不补满。具体条件逐股预先讨论，不设普适涨跌幅触发值。
- 每个未执行批次同时预设复核节点（日期或关键事件）；节点到达而条件未出现时，重新评估原逻辑、估值、风险与时机，不自动买入也不自动取消。
- 关键假设变弱或风险不合适时暂停未执行批次并复核。
- 该框架尚未验证，依实际体验调整。

## 4. 未执行买入批次状态

**状态集合**：待条件（正常等待）｜风险暂停待核实｜待你确认｜继续等待/调整条件｜已放弃。

**暂停范围**：风险只影响某批预设条件 → 只暂停该批；触及各批共同依赖的核心假设 → 暂停该股全部未执行批次。证据不足标待核实，只暂停明确受影响批次，不贸然扩大。记录受影响假设、批次、原因、待核实证据、恢复条件；一批涉及多风险时逐项登记，**任一相关风险未解决即维持暂停**。

**风险解决判定**：只接受可靠可核验的证据表明原信号已消退／传导路径不成立／实质影响已排除。🔴 **单纯没有新消息、报道减少、暂时未见影响都不算**。记录判断依据、证据来源与日期、被排除的环节、剩余不确定性。

**风险重开**：后续可靠新证据表明已解决的风险重现，或原判断不成立 → 立即重开，按原暂停范围执行；有实际持仓的同步复核持仓逻辑，区分行业事实／传导推断／公司端证据。

**静默规则**：首次报告后，无实质新证据则静默；只在实质新证据或到达约定复核节点时更新。到节点仍无新证据 → 继续保持暂停并设下一节点，**不自动恢复、不进入固定周期提醒**。

**状态转换边界**：🔴 全部相关风险复核并报告后，**在收到用户明确选择前仍保持「风险暂停待核实」**，不自动转其他状态。用户选「继续等待」按其决定记录；选「调整条件」时仍保持暂停，**直至双方明确商定新条件及复核节点**才转「待条件」；确认放弃才标「已放弃」。

**🔴 风险暂停期间**：即使原定价格/建仓条件满足，也只记入台账 —— **不解冻、不触发买入前门禁、不做买入评估**。不自动买入、卖出或取消。

**实质新证据** = 可靠、可核验、可能改变传导判断或公司端影响评估的新事实/数据。重复报道、无来源传闻、纯价格波动**不算**。

## 5. 提醒触发（持仓相关）

- **行业前瞻风险**：可信且与原投资理由/产业链明确相关的全球、外部或国内行业信号出现时提醒并标「前瞻风险」，写明行业事实、潜在传导链、未核实的公司端证据。**不直接判公司逻辑走弱/失效。** 一般或关联性弱的动态纳入定期回顾，不单独推送。
- **逻辑变化分级**（每只记录原投资理由、可观察指标/事件、可靠来源及更新时间），按「全球及外部行业 → 国内行业 → 向目标公司的传导 → 公司经营/财务验证」**逐层检查**，覆盖供需、价格、技术/替代、产能/资本开支、政策/贸易限制、竞争格局及上下游。证据成熟度分层：

| 层级 | 判定 | 动作 |
|---|---|---|
| 仅有行业信号、传导不清 | 前瞻风险/待核实 | 不判公司逻辑受损 |
| 传导路径可信，公司端未验证 | 提醒复核 | 列待查公司证据、区分事实与推断 |
| 公司端对应变化经可靠证据验证 | 按影响程度 | 才可判逻辑走弱/失效 |

🔴 **股价下跌本身不等于逻辑失效**；来源/口径/传导链/公司验证不足一律列待核实；提醒只触发复核，**不自动卖出**。

优先级、质量要求、降噪与静默规则见 `ashare-notification-spec`。

## 6. 仓位与退出规则检查

记录并检验：
- 仓位分母（股票仓位？全部可投资资产？）— 必须问清。
- 参考成本（用户可指定用收盘价代作，但须标明非成交回报）。
- 退出阈值 + **触发口径**（盘中/尾盘/收盘确认）+ 委托方式。
- A股连续竞价/收盘集合竞价时段仅在解释用户指定的某个具体历史或当前交易规则时再核实；不据此建立价格止损或提醒。
- 🔴 **不在整体流程中默认设置固定比例价格退出线。** 台账逐笔保存交易事实，不按批次另设未经确认的价格退出线。
  ⛔ **例外：模块二「亏损保护」的 −8%/−15% 两档是本工作流明确要求的功能，不是旧版那种默认止损线** —— 它只通知、不授权交易，且必须同时报告公司端证据。
- **止损价不是亏损上限**：A股跌停/跳空/停牌会使实际成交偏离阈值（曾实测某持仓股单月多次单日-10%跌停）。

## 7. 组合风险检查（持有多只时必做）

用日收益序列计算，**全部标注“测算/回测，非指令”**：

| 指标 | 算法 |
|---|---|
| 日波动 | pstdev(日收益) |
| 年化波动 | 日波动 × √252 |
| 相关性 | 两股日收益 Pearson ρ |
| 风险贡献 | 边际贡献 `w_i(w_i·σ_i² + w_j·ρσ_iσ_j)` 占组合方差之比 |
| 等风险贡献(ERC)权重 | 两资产：`w_a = (1 − ρ·σ_b/σ_a) / (2(1−ρ))` |
| 组合波动 | `√(w_a²σ_a² + w_b²σ_b² + 2w_aw_b·ρσ_aσ_b)` |
| 历史最大回撤 | 净值路径的 peak-to-trough |

- **核心洞察要主动指出：资金权重 ≠ 风险权重。** 高波动标的即使资金占比低，也会主导组合风险。
- **共振检验（最有价值）：** 统计“当标的A的N日跌幅≥阈值时，标的B同期也跌超阈值的比例”，直接揭示“分散”是否真实存在。
- **止损噪音检验：** 某标的N日跌幅≥止损阈值的概率；若止损宽度只相当于1–2天正常波动，说明信号里混着大量噪音。
- **止损有效性回测：** 逐日模拟触及阈值即清仓转现金，计算组合最大回撤。**必须检查代码正确性**——把“清仓”误写成“乘以0”会得到荒谬的-100%。

## 8. 按账户回撤容忍度反推仓位

**顺序很重要：先问“账户从高点跌多少你拿不住”，再用数据反推仓位，而不是先定仓位。**

1. 网格搜索：多个总仓位 × 分配比例 → 历史最大回撤。
2. 找出回撤 ≈ 用户容忍度的仓位区间。
3. 对照：带止损 vs 无止损的组合回撤差异。

**注意反向发现：** 用户已有的止损规则可能已恰好把回撤控制在容忍度内。此时真正的决策点不是“止损该不该放宽”，而是“能否接受止损被噪音频繁触发”。若不能 → 放宽止损（推高账户回撤）或降低仓位（降低资金效率），二者必择其一，**把权衡摆给用户，不替他决定**。

## 9. 持仓管理三模块（本工作流裁定·适用于所有持仓股）

**三个模块都只通知、不下单。** 买卖全部由用户决定与执行。
🔴 **本节取代旧版单一「盈利保护 = 成本 + 2×ATR」** —— 旧公式在浮亏状态下永远不触发
（浮亏时阈值挂在成本之上，股价要涨回去才报警），已废弃。

### 9.0.1 峰值口径（本工作流裁定）

**峰值 = 台账首次买入日 → 今的日K最高价，脚本每次自动重算，不由人手填。**

用户原话：「峰值不应该是我持仓以来的日最高值吗……跟每日没啥关系」。

- 🔴 **为什么不算用户输入**：峰值是市场客观数据，能算就不该人填；手填会随每次新高过期，而监控每天都要用；且混在台账里分不清哪些是客观行情、哪些是用户风控边界。
- 🔴 **与持仓多少无关**：加仓/减仓都不改变峰值口径。
- 用**日K最高价**、含买入当日，不用盘中实时最高 —— 否则峰值基准会在 11:20 / 14:40 两点间不一致。
- 前复权口径内自洽即可算回撤率；与当日现价同源可直接相除。
- 峰值不可得（如台账无交易记录）→ 报 `NEED_DATA`，不猜。

### 9.0.2 台账 vs 脚本的分工

| 内容 | 由谁提供 |
|---|---|
| 交易日期 / 方向 / 数量 / 成交价 | **用户通知**（台账《交易记录》逐笔）|
| 加权成本 | **脚本自算** `Σ(价×量)/Σ量`，用户值降为交叉校验 |
| 峰值 / 回撤率 / 浮盈亏 / ATR | **脚本自算** |
| 两档回撤 / 两档亏损线 / 单股仓位上限 | **用户手填**（风控边界，脚本无权代设）|

🔴 用户买卖后必须先确认**当日是否为交易日**，再写入台账 —— 非交易日成交要么记错日期，要么是场外成交，两者都会让峰值起点和成本算错。

### 9.0.3 交易入账流程（🔴 本工作流裁定，不得跳过）

用户买卖后通知你，按顺序执行，**不得跳步**：

| 步 | 动作 | 🔴 红线 |
|:-:|---|---|
| 1 | **先确认当日是否为交易日**：`python3 scripts/trading_day.py <YYYY-MM-DD>` | 判为休市 → **先问用户**，不得直接写入 |
| 2 | 核对方向、数量、成交价（含手续费口径），**向用户复述一遍求证** | 数字不对就别写 |
| 3 | 写入台账《交易记录》一行（含**完整 ISO 日期**，不写「约14:40」当日期）| 不得补造未确认的细节 |
| 4 | 加权成本由脚本重算，**把算出的值报给用户核对** | 与用户券商App不一致 → 报 `NEED_DATA`，不自行取舍 |
| 5 | 峰值从新交易日重算（首次买入日变动时**峰值起点随之变**）| 减仓不清除峰值；清仓则归档不再监控 |

#### 🔴 交易日判定：绝不能用「周一至周五=交易日」

**实测反例**（某大盘股前复权日K，国庆休市期间）：

```
2026-09-25← 周五，K线里不存在（国庆休市）
...
2026-10-07  ← 周三，K线里不存在（国庆休市）
2026-10-08  ← 周四，节后首个交易日
```

节假日 + 调休工作日会让粗判错得很离谱：**调休的周六是交易日，春节所在的周五是休市**。

正确判据：**休市日不产生K线**。用 `scripts/trading_day.py`，三层判定：

| 层 | 判据 | 说明 |
|---|---|---|
| 1 | 周末 | 必休市 |
| 2 | 日K 交易日列表 | **权威**。取 ≥300 根 —— 窗口太短会把整个长假判成交易日|
| 3 | 腾讯实时报价时间戳 | 休市日停在最近收盘 |

🔴 **不得硬编码节假日表** —— 每年由国务院公布，硬编码会过期且无人记得更新。
🔴 **判定失败一律按「不是交易日」处理** —— 宁可不记，也不要在休市日默默写入一笔成交。

#### 持仓期峰值起点会随交易变动

| 事件 | 峰值起点 | 峰值 |
|---|---|---|
| 首次买入 | 该买入日 | 从该日起算 |
| 加仓 | **不变** | 不变 |
| 减仓 | **不变** | 不变 |
| 清仓 | 归档，不再监控 | — |

#### 仓位上限三种写法（本工作流裁定）

| 台账写法 | 含义 | 特点 |
|---|---|---|
| `10,000 股`（示例值） | 股数上限 | **死的** —— 涨到天上也加不了 |
| `140 万元` | 金额上限（比**市值**）| **活的** —— 股价跌了自动腾出加仓空间 |
| `30%` | 组合占比 | 折算股数需账户总额，脚本不知 → 只报上限 |

🔴 三种单位含义完全不同，混用会让加仓模块算出荒谬的「还能买多少」。

| 模块 | 锚点 | 触发线 | 档位 | 建议动作 |
|---|---|---|---|---|
| **一·盈利保护** | **峰值**（持仓期最高价）| 峰值×(1−X) | 🟡 −12%／🔴 −20% | 减 1/3 ／ 再减 1/3 |
| **二·亏损保护** | **成本** | 成本×(1−X) | 🟡 −8%／🔴 −15% | 预警 ／ 三选一决策 |
| **三·加仓建议** | 仓位空间 | 见 9.3 六场景 | 单次 ≤1/3 目标 | 加 1/3 或 1/4 |

🔴 **锚点不可混用**：盈利保护锚「峰值」（保护浮盈），亏损保护锚「成本」（保护本金）。
🔴 **模块一判定不能只看「现价 vs 成本」** —— 峰值回撤保护的是**浮盈退潮**：只要峰值回撤达档，即使现价已跌回成本下方也照样报（否则「涨过又跌回」这段最该提醒的区间会静默）；现价 < 成本而回撤未达一档时，报「浮盈吃光」RED 并转入亏损保护决策。**仅当峰值不可得**（台账无《交易记录》）时，才按现价与成本归口：现价 < 成本 → `N/A` 归模块二。

### 9.1 模块一：盈利保护（峰值回撤口径）

```
触发线 = 持仓期最高价 × (1 − 回撤档)
```

**峰值（Peak）维护规则**（口径见 9.0.1，🔴 不以本节旧描述为准）：
- **峰值 = 首次买入日 → 今的日K最高价（含买入当日），脚本每次自动重算** —— 🔴 不由人手填、不写进台账当参数
- 用**日K最高价**、不用盘中实时最高 —— 否则峰值基准会在 11:20 / 14:40 两点间不一致
- 🔴 **加仓 / 减仓不改变峰值口径，也不清除峰值** —— 保护的是总浮盈，不是单批成本
- 清仓后归档，不再监控
- 峰值不可得（台账无《交易记录》，或首次买入日落在取K窗口外）→ 报 `NEED_DATA`，不猜

**两档与建议动作**：

| 档 | 回撤 | 建议 | 依据 |
|---|---|---|---|
| 🟡 一档 | **−12%** | 减 1/3 仓位 | 实测：回撤 10% 后约 51% 概率继续跌——**一半是噪音** |
| 🔴 二档 | **−20%** | 再减 1/3 仓位 | 实测：回撤 20% 后仅 32% 继续跌——**已跌透，此时卖可能卖在低位** |

🔴 **档位可逐股覆盖**，按波动率校准（建仓时定，写台账）：
```
ATR% > 5%（高波动）→ 放宽到 −15% ／ −24%
ATR% < 3%（低波动）→ 收紧到 −8%  ／ −14%
默认 → −12% ／ −20%
```
**观察点**：交易日 11:20 ＋ 14:40，判定**一律用实时价**，🔴 不得改用日K收盘价。
🔴 **未达档位即静默**——不许每天推无意义报告。
⚠️ **同一档位只提醒一次**；档位状态变化或用户已处理后才可再报。

### 9.2 模块二：亏损保护（成本锚定）

```
🟡 预警线 = 成本 × (1 − 8%)     提前知情，不建议动作
🔴 止跌线 = 成本 × (1 − 15%)    决策点
```

**三态必须分开报**：

| 状态 | 判据 | 输出 |
|---|---|---|
| 正常 | 现价 ≥ 预警线 | **静默** |
| 🟡 预警 | 跌破 −8% | 已跌 X%、距止跌线 Y% ＋ **公司端是否有硬信号** |
| 🔴 止跌 | 跌破 −15% | 已跌 X% ＋ **建议三选一** ＋ 公司端证据 |

🔴 **🔴 触发时必须同时报告公司端证据** —— 区分「纯价格波动」与「真有什么坏了」。
这个区分决定「割」还是「扛」，**不能只报价格**。

**跌破 −15% 时的三选一**（只列选项，🔴 不替用户选）：
1. **止损**：减 1/2，保住本金
2. **等待**：基本面未失效则不动，设定下一观察点
3. **加仓**：若符合 9.3 且有仓位空间

### 9.3 模块三：加仓建议

#### 🔴 前置条件（缺一不可，缺则直接报「无法给建议」）

```
① 已有仓位 < 单股仓位上限     ← 🔴 没上限则本模块空转，必须先定
② 投资逻辑未失效（现金流/扣非/核心假设仍成立）
③ 剩余仓位空间 ≥ 建议加仓量
```

#### 六场景与上限（A–F）

| 场景 | 触发 | 单次上限 | 硬门槛 |
|---|---|---|---|
| **A 下跌·深度回撤** | 从峰值回撤 >30% **且** 基本面未失效 | 1/3 目标仓位 | 逻辑未失效 + 有仓位空间 |
| **B 下跌·技术确认** | 跌至 MA60/前期平台 **且** 缩量止跌 | 1/3 目标仓位 | 同上 |
| **C 下跌·逻辑验证** | 股价跌 **但** 扣非/现金流同比改善（背离）| 1/4 目标仓位 | 同上 |
| **D 首次未满** | 分批计划还有未执行批次 | 按原计划 | 同上 |
| **E 下跌·已浮亏−15%** | 命中 A/B/C **且无公司端硬信号** | 🔴 **降档到 1/4** | 🔴 有硬信号则**禁止加仓** |
| **F 上涨·突破回踩** | 突破成本+X% **且回踩不破** **且量价配合** | 1/4 目标仓位 | 见下 |

> 📌 **字母口径以交接文档《持仓管理三模块框架》§二 为准**：**E = 浮亏 ≥15%（降档 1/4）、F = 上涨加仓**。其他文档与脚本均引用 `A–F`、不展开字母语义，**勿单方面调换字母**。

🔴 **场景 F（上涨加仓）必须同时满足四条，缺一不提**：
1. **回踩确认** —— 突破后回踩不破（日内假突破太多，宁可错过）
2. **量价配合** —— 上涨放量、回调缩量
3. **逻辑仍在强化** —— 基本面向好（🔴 股价涨≠逻辑好）
4. **目的是扩大战果，不是解套** —— 解套型加仓按场景 A-F 走

🔴 **上涨加仓的 X 值逐股在台账里定，不设通用值。**
理由（实测）：同为 A 股、同样的「突破成本+X% 就加仓」规则，
某周期股 60 日后相对成本 **−5.1%（50/66 次变亏）**、某成长股 **+34.0%（仅 4/297 次变亏）**——
**同一条规则在周期股与成长股上结果相反**，按历史外推必然出错。

#### 🔴🔴 满仓时 F 与 X 只是「暂时用不上」，绝非停用（本工作流明确）

- 仓位上限＝当前持仓数（已满仓）→ 前置条件①「已有仓位 < 单股仓位上限」不满足
  → **模块三全场景（含 F）自动不适用**。
- ⛔ **这是「本次用不上」，不是「停用 F」也不是「取消 X」**。
  **F 与 X 长期有效**：一旦有加仓空间（上限调高、或减仓腾出空间），
  A–F 与 X 值**立即生效**，无需重新启用。
- 🔴 **满仓是仓位状态，不是规则状态** —— 不得把两者混为一谈。

#### 🔴 四条禁止加仓（硬规则，优先级最高，覆盖一切）

```
① 触发任何失效硬信号（现金流/扣非转负、逻辑走弱）
② 已跌破 −15% 止跌线 且 公司端有硬信号
③ 单股仓位已达上限
④ 组合层风险过高（见下）
```

#### 🔴 组合层前置检查（每次给加仓建议都要跑）

```
当前该股占比 + 建议加仓后占比 ≤ 单股仓位上限
该股波动率 × 权重 是否已主导组合风险（资金权重 ≠ 风险权重）
与其它持仓的日收益相关性（高相关时加仓＝放大单点风险）
```

### 9.4 通用纪律

- 🔴 **三个模块的**手填**参数（两档回撤、两档亏损线、仓位上限）都写在台账里，脚本只读不算。** 风控边界不该由脚本拍板；**峰值例外 —— 属市场客观数据，脚本自算**（见 9.0.1）。
- 🔴 **价格类现象一律不是失效条件**，只触发复核；失效只由公司端证据判定（沿用本步红线）。
- 🔴 **同一档位只提醒一次**；状态变化、用户处理后、或到达约定复核节点才可再报。
- 🔴 **建仓初期「浮盈吃光」RED 是已知必然现象，先挂着不动** —— 建仓几天内峰值≈成本，模块一必然报 RED，不是故障。
- 提醒须说明：剩余数量、盈亏口径、保护线依据、**公司端证据有无**。
- 资料不足先问或标未知，🔴 **不猜成交数量/价格**。

### 9.5 🔴 单股仓位上限是硬前置

**没有仓位上限，模块三整个空转**（算不出「还能买多少」）。
建仓时必须问并写入台账（见 9.3 前置条件①）。
⚠️ 未设上限的持仓，模块三直接报「无法给加仓建议·缺仓位上限」，**不猜一个数出来**。

## 10. 台账文件与引用规范

底账在 `$STOCK_DATA_DIR/股票台账/`：
- `流程状态表.md` —— **只记哪些股票在第几个阶段**（标的/代码/当前阶段/台账链接/最近更新）
- `组合总览.md`；每只股票一份持续更新的 `持仓中/{名称}_{代码}_跟踪台账.md`（候选期放 `候选/`，清仓后移 `已清仓/`）
- 交易台账不按日期另存副本；历史分析报告与决策日志在 `$STOCK_DATA_DIR/`

**建档**照 `股票台账/模板/单股跟踪台账_模板.md`，**按模板末尾《建档索取清单》向用户索取信息**（缺项写「待补充」，不推算不杜撰）。必问：方向与日期、成交价与数量、原始理由原话、失效条件、是否已全部卖出、计划持有期。🔴 **成交价一律视为含手续费**，无需索取费用明细。

**双写**：用户报告成交后先更新个股台账（交易明细/次数/成本/价格线/盈亏），再更新 `流程状态表.md` —— 🔴 **只在阶段变化时改阶段行**，具体状态不进状态表。两处矛盾时以台账为准。

必备章节：档案信息 → 投资逻辑与持有计划 → 交易记录 → 价格线与计划（仅用户确认的）→ 可核验数据与证据 → 持仓复核与风险 → 复盘与决策对照 → 待确认事项。

引用规范用 `grounded-citations` 技能（`scripts/sources.py`）：财报类必须 `--evidence` 逐字校验，摘要用 `--style evidence --replace-in`，**不要手打 URL**。

## 11. 自动监控配置（适用于所有持仓）

**每只新股票进入第7步时直接按下表配置，不临时商量拆法。**

| 任务 | 粒度 | 频率 |
|---|---|---|
| **三模块监控（盈利/亏损/加仓前置）** | ⭐ **全部持仓合 2 个**（一个脚本扫「持仓中/」目录逐只判定）| 交易日 11:20 ＋ 14:40 |
| **重大公告与逻辑风险扫描** | ⭐ 全部持仓合 1 个 | 交易日 20:30 |

🔴 **这两个观察点任务是 `no_agent`（prompt 为 0 字）**，规则全在脚本里 —— **不要靠改 prompt 配置，改脚本**。

🔴 **新增持仓固定动作**：
1. 在「持仓中/」目录按模板新建该股台账（文件名 `{名称}_{代码}_跟踪台账.md`）—— **建台账即自动纳入监控，不改任何代码**；成本、持仓量一律由台账《交易记录》算（Σ价×量/Σ量、Σ买−Σ卖）。
2. 台账补齐 4 个**手填**参数：盈利保护一档/二档回撤、亏损保护预警/止跌回撤、单股仓位上限。
3. 复跑 `python3 scripts/validate_ledgers.py`（第 9 项会拦旧口径残留）。
4. 跑 `python3 scripts/profit_guard.py --with-json` 确认该股不是 `NEED_DATA`，且无「台账自相矛盾」告警。

公告与周度**不新建**任务，在它们 prompt 的持仓清单里加该股即可。

🔴 **峰值与仓位上限缺失时的行为**：模块一报 `NEED_DATA·缺峰值`，模块三报 `NEED_DATA·缺仓位上限`——
**🔴 不得用内置默认值兜底**（那等于助手自行设定风控边界）。
例外：模块二只需成本，**不受影响可正常判定**。

## 12. 执行边界（不可逾越）

- **助手永远不执行买入、卖出或任何交易委托。** 所有交易由用户本人决定并操作；分析、门禁讨论、价格提醒都不是下单授权。
- **仅当用户告知实际买卖结果后**，才据此更新底账和决策日志。自动监控只做有范围限制的证据扫描/盈利保护启动条件检查，不能更改持仓数量、生成未确认的价格线、买卖或创建新任务。
- 用户决定不买或继续跟踪时，不得建成持仓、不得启动持仓止损监控；如本工作流明确要求可设候选观察提醒，但须与持仓任务区分。
- 用户卖出后，确认清仓事实再停止该标的持仓提醒；保留历史底账和操作记录，不删除历史。

## 三模块判定：优先用 Python 前置
三模块的阈值判定（峰值回撤档、成本亏损线、仓位上限比对）都是纯算术，不要每次调大模型重算。
先跑 `scripts/profit_guard.py --slot <11:20|14:40>`，按 JSON 的 `action` 与各模块 `status` 分支：
`SILENT` 直接结束（不发飞书/邮件）；`REVIEW`/`NEED_DATA`/`FAULT_ONCE` 才介入复核。
详见 references/python-precheck.md。

台账更新 + 风险/保护结论 + 待确认事项产出即停；只提醒不交易，等待用户决定。

## 🔴 阶段变更 = 更新流程状态表（三层保障）
